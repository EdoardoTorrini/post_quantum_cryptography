RSA, EC cryptography and lattice-based cryptography depend not only on the hardness of numberic problem, but also on the security properties of cryptography hash function.
Hash-based signature scheme are first proposed by **Leslie Lamport** in 1975 followed by important improvements by **Winternitz** and **Merkle** in 1979
-> unique advantages: the only cryptographic primitive employed is a hash function.

PRO: resists against both classical and quantum attacks
CONTRO: large public keys and large signatures

Standardize hash-based signature scheme:
1. Leighton-Micali Signature Scheme (LMS) [ NIST SP 800-208 or RFC 8554 ]
2. eXtended Merkle Signature Scheme (XMSS) [ NIST SP 800-208 or RFC 8391 ]

both LMS and XMSS are classified as **stateful** signature scheme, because the signer must keep track of some non-secret data called state.
properly storing and updating the state is critical for the security of LMS and XMSS.

3. SPHINCS+ [ FIPS 205 ]: is a **stateless** signature scheme that eliminates the need for tracking non-secret data.

## Hash Function
1. Definition of hash function, some notes: 
    - H is called an n-bit hash function
    - H(x) is called hash or message digest of x 
    - The description of hash function is public, and no keys are needed
2. Security requirements:
    - Pre-image Resistance (One Way)
    - Secondo Pre-image Resistance
    - Collision Resistance: since the domain of H is tipically much larger than its sub-domain collision must exists by the pigeon hole principle.
      The key question is not their existance but whether any one collision can be found efficently.

There are some type of relations between this security requirements:
1. if a hash function is collision resistant, the is also second pre-image collision resistance.
2. collision resistant implies pre-image resistance, provided that the hash function is somewhat uniform, meaning that each hash value has approximately the same number of pre-images.
3. pre-image resistance does not guarantee second pre-image resistance.
4. 2PR imply PR for somewhat uniform hash function.
5. 2PR does not imply CR.
6. PR does not imply CR.

From this relationships, we see that collision resistance is the strongest of the three properties. A collision resistance hash function is necessarily both PR and 2PR.
The converse is not true. (is possible to proof this result in video V3b of Crypto 101: Building Blocks)

3. Classical Attack (running time of fastest generic attack)
    - finding PR: 2^n operation
    - finding 2PR: 2^n operation
    - finding CR: 2^{n/2} operation -> using VW parallel collsion search (V3c of Crypto 101: Build Blocks)
4. Quantum Attack (runngin time of fastest / most cost-effective generic quantum attack)
    - finding PR: 2^{n/2} operation (Grover's search)
    - finding 2PR: 2^{n/2} operation (Grover's search)
    - finding CR: 2^{n/2} operation -> using VW parallel collision search

using SHA-2 or SHA-3 (check the security level of the version against classical attacks and quantum attacks)
-> SHA-2 and SHA-3 are suitable for hash-based signature schemes in the post-quantum world.

## Lamport one-time signature scheme
Starting from describe the toy version: signing a single bit
Consider G: {0, 1}^n -> {0, 1}^n is a preimage-resistant hash function

1. Key Generation: Alice select x0, x1 \in {0, 1}^n, and computes y0 = G(x0) e y1 = G(x1).
   In this case X = (x0, x1) is her private key and Y = (y0, y1) is her public key.
   Observe that computing the private key from the public key is infeasible because we consider the hash function G to be preimage resistant.
2. Signature Generation: To sign a bit m \in {0, 1}. Alice sets S = Xm. (To sign 0 -> x0, instead to sign 1 -> x1). Her signed message is (m, S)
3. Signature Verification: Anyone who possesses an authentic copy of Y can verify that Ym = G(S)

The single bit signing scheme can be generalized to allow signing messages of arbitrary bit lengths.
In this case we consider two different hash function:
  - G: {0, 1}^n -> {0, 1}^n is a preimage-resistant hash function
  - H: {0, 1}^* -> {0, 1}^n is a collision-resistant hash function that maps inputs of any bit lengths to n bits output

1. Key Generation: Alice select x_{i, j} \in_R {0, 1}^n for i = 0, 1 and j = 0, 1, ..., n - 1. Compute y_{i, y} = G(x_{i, j}).
		   Alice sk is X = (x_{i, j}) and pk is Y = (y_{i, j})
2. Signature Generation: to sign a message M \in {0, 1}^*, Alice compute H(M) = m = (h_0, h_1, ..., h_{n - 1}).
			 Her signature for message M is S = (s_0, s_1, ..., s_{n - 1}) where s_j = x_{i, j}
3. Signature Verification: to verify (M, S) anyone who possesses an authentic copy of Y can compute h = H(M) and check that y_{i, j} = G(s_j) for j = 0, 1, ..., n - 1

OTS: a signed message (M, S) expose an half of the component of Alice's private key. A second signed message (M', S') is expected to expose an additional quarter of 
     Alice's private key components.
     -> Alice to preserve the security should sign only one message using the same private key. 
     	-> Lamport's signature scheme is classified as One Time Signature scheme (OTS)

SECURITY
Definition: A one-time signature scheme is said to be secure if it is existentially unforgeable by a computationally bounded adversary who is permitted to obtain
	    the signature for one message of the adversary's choosing (oracle)

EFFICIENCY
Private key and public key size: 2n^2 bits (for n = 256 -> bit length is: 16,384 bytes)
Signature size: n^2 bits (for n = 256 -> bit length is: 8,192 bytes)

Key Generation Time is 2n evaluation of the G hash function.
Signature Generation is 1 evaluation of the H hash function.
Signature Verification is 1 evaluation of the H hash function and n evaluation of the G function.

## Lamport: Problems and Solutions
OTS has the dimension of the signature, private key, and public key that are very large than the common standard like RSA and ECDSA.
To reduce the private key size, the private key components x_{i, j} are generated from a randomly selected secret endbit seed and a counter using a Pseudorandom Funciont (PRF)
  -> x_{i, j} = PRF(SEED, i, j)

For example the PRF could be an HMAC with the seed serving as a secret key. The seed is securely stored, and used to generate the x_{i, j} when needed.
This permit to reduce the private key size from 2n^2 bits to n bits. For example with n = 256 -> the sk size can be reduce from 16,384 bits to 256 bits (32 bytes).

The other problem is the size of pk (2n^2 bits) and the size of sign (n^2 bits), the large size of the signature is conseguences of the facts the message - H(M) -
are signed one bit at time.
  -> The solution (Winternitz, 1979) is to sign w-bit block at time using hash chains

Hash chains: is created by repeatedly applying a PR hash function to a randomly chosen initial value.
  -> descript in the slide

Winternitz OTS: use the hash chain and the csum to resist to existential forgery.

EFFICIENCY
Suppose that n=256 and w=8 (so a hash chain has length 255), then l1=32 (l1=n//w -> number of blocks in h), l2=2 (l2=log2(l1(2^w-1))/w+1 -> number of blocks in csum(h)), and l=l1+l2=34.
The public key size is 1,088 bytes (vs. 16,384 bytes for the Lamport OTS).
The signature size is 1,088 bytes (vs. 8,192 bytes for the Lamport OTS).
The private key size is 32 bytes (using a secret seed and PRF).

Both the Lamport and Winternitz OTS scheme share the same limitations: that a private key can only sign securly only one message.
This is impractical for most applications due to the significant overhead of securely distributing public verification keys, for example, through certificates.
Ideally the public key should be small, and, also, the private key should be small and permitted to securely sign many message.
  -> generate many Winternitz OTS key pairs, and use them one at time.
    -> need a large number of OTS keys if you expect to sign a large number of message. The total size of all the OTS pk is very large
      -> use a Merkle tree to authenticate the OTS pk

Main Idea: build a complete binary tree whose leaves represent the hashes of the individual OTS pk. 
Each internal node's value is obtained by hashing the concatenation of the values of its two children recursively building up to a single root hash.
The user's long-term public key is the value assigned to the root of the tree.
Authentication paths to the root are used to confirm the authenticity of an individual OTS pk.

The security relies on the collision resistance (CR) hash function F.

EFFICIENCY v2
Winternitz parameters: n=256, w=8, l=34.
Merkle tree: Height 20 (so 2^{20} Winternitz OTS key pairs)
 -> Long term public key size: 32 bytes
 -> Private key size: 32 bytes (using a secret seed and PRF)
 -> Signature size: 1,088 + 1088(Yi) + 20 * 32 (auth.path) = 2,816 bytes

Thus, the Merkle Tree results in a very smallo long-term public key, substantially increased functionality, allowing 1 million signatures without changing the long term public key, 
and only a modest increase of the signature size.

! Problem: constructing a large Merkle tree is slow, 2^d OTS (d is the height of the tree) key pairs need to be generated in order to determine the root R (long-term public key) of the tree.
  -> the Merkle tree is divided into smaller trees to form a hypertreee, also called multi-tree

## Leighton-Micali Signature Scheme
  -> combine WOTS with Merkle tree (RFC 8554) in the RFC are described three different type of signature scheme:
    -> LM-OTS: one time signature scheme
    -> LMS: LM-OTS + Merkle tree
    -> HSS (Hierarchical signature scheme): LMS + hypertreee
  LMS was adobted as NIST standard in 2020 (SP 800-208), pointing to the RFC 8554 adding some parameters sets.

XMSS (eXtendable Merkle Signature Scheme): is another hash-based signature scheme, standardize by the IETF (RFC 8391) and by NIST (SP 800-28).
  -> is very similar to LMS

### LM-OTS
is the WOTS with some modifications. it use the same parameters as WOTS. in the SP 800-28 is admitted for w only a values from the set {1, 2, 4, 8}
in that way the only hash chain length admitted are {1, 3, 15, 255} respectively.

1. The first difference is in the public key (pk), in WOTS the pk is Y = (y0, y1, ..., y_{l - 1}), instead in the LM-OTS the pk is K = H(y0 || y1 || ... || y_{l - 1}).
  -> these final hash chain values can be derived from any signed message, the signature verifier can always reconstruct the pk K, during signature verification.

2. The LM-OTS use a single hash function H: {0, 1}^* -> {0, 1}^n.

3. In the LM-OTS a unique prefix is appended before hashing operation to support security proof.
   This prefix ensure that each hash function invocation remains indipendent.
   The prefix includes:
     -> a randomly selected 32 bytes identifier string I of the Merkle tree associated with the LM-OTS istance.
     -> a 4-bytes number q that identifies the tree's leaf associated with the LM-OTS istance.
     -> the index i of the w-bit block h_i within the message hash/checksum, wich determines which hash chain to use.
     -> the position j within a Winternitz chain.
     -> 2-bytes constant: 0x8080 (for computing K) or 0x8181 (for hashing a message)

4. A randomly-generated 256-bit string C is appended to the message M before hashing: h = H(C || M)
     -> C is called the message randomizer.
     -> C is included with the signature, since it's needed for signature verification
   This eliminates the need for CR for H (since C is randomly chosen byte the signer each time a message is signed).

### LMS
use a height-d Merkle tree, whose leaves are associated with LM-OTS public keys K0, K1, ..., K_{2^d - 1}. so the total of 2^d keys.
in the SP 800-208 are admitted like height-d parameters only {5, 10, 15, 20, 25}. and all private key (sk) are generated from a 256-bit random secret seed.
  -> the ith component of private key associated with the leaf number q is H(I || q || 0xff || seed).

the number of leaf of a Merkle tree are numbered sequentially from left to right and top to bottom. the long-term public key is the root of the Merkle tree.

SECURITY
The enhancements introduced by Leighton and Micali to their signature scheme, including the use of unique prefix for all hashed data, enables a formal security 
analysis of LMS.
  -> Katz, 2016: proven security in the random model.
  -> Eaton, 2018: LMS is proven secure to quantum random oracle model. (adversary can query H in superposition)

### HSS is the hypertreee version of LMS 
  -> SP 800-208 permits hypertreee with as many as 8 layers.

Use cases for HSS include scenarios where an entity anticipates signing a large number of messages during the lifetime of their long-term public key.
Or if the entity needs to delegate signing privileges to two or more cryptography modules while the risk of OTS private key reuse.

### XMSS
  -> is very similar to LMS.

The main difference is its use of "bitmarks", which are pseudorandom bit string that are XORed with inputs to the hash function. 
The bitmarks enable security proofs for XMSS in the "standard model", wihtout needing to model the hash function as a random oracle.
The hypertreee version of XMSS is called XMSS^{MT}, both are fully specified in RFC 8391, and additional parameters sets are defined in SP 800-208.

LMS and XMSS are stateful signature scheme. A signer must be very careful not to reuse any of their OTS sk associated with their long-term pk.
To enforce this requirements, the signer could keep track of a counter or key index that increments after each message is signed.
  -> this type of data changes over time is called STATE.
However maintaining state securely in practice can be challenging, if a system crashes and is restored to an earlier state, 
the OTS sk might be reuse and security would be compromised.
So stateful signature scheme are suitable for applications where state can be reliably managed. 
For example, to authenticate software updates where signing is quite infrequent.

## SPHINCS+
LMS are stateful because must be track of which OTS keys have been used to sign the current message in order to ensure that an OTS sk is never reused
instead SPHINCS+ is a signature scheme stateless.

SPHINCS+ was designed by Bernstein, Hulsing, Kolbl, Niederhagen, Rijneveld and Schwabe and was standardize by NIST in August 2024 (FIPS 205) is official name is SLH-DSA
(Stateless Hash-based Digital Signature Algorithm)

The main idea is to use an hypertree with a very large number of leaves, each one represent signature key pairs for an OTS.
To sign a message, the signer randomly selects one of these key pairs. A limit is placed on the total number of msg that can be signed,
ensuring that the probability of key reuse is negligibly small.

SPHINCS+ employs numerous optimizations. The two main optimizations: few-times signatures and virtual hypertrees.

### Few-times signature schemes (FTS)
Unlike a OTS scheme, a few-times signautre scheme (FTS) can be used a small number of times (ex. 5-10 times) before security degrades.
The main idea is that each signature reveals only a small fraction of the private key components, unlike Lamport's OTS where a signle signature reveals half of the sk.
  -> HORS

HORS SECURITY ANALYSIS
Suppose the adversary has obtained `c` signed messages (M_i, (C_i, S_i)), since the randomizers C_i were chosen by Alice, the adversary has no control over the hash values 
h(i) = H(C_i || M_i)
Assuming that H behaves like a random function, the `c` signed messages reveal at most `ck` randomly-selected components of X. To forge Alice's signature, the adversary needs to find
a message M^* and randomizer C^* such that each x_{h_j^*} (where h^* = H(C^* || M^*) = (h_0^*, h_1^*, ..., h_{k-1}^*)) is among the revealed components of X.
  -> this happens with probability at most (ck/t)^k: if this probability is negligible, Alice can securely sign up to `c` messages.

Example: suppose n=256, k=16, m=16, t=2^{16}, and c=5
  -> then the probability defined on the previous slide is (ck/t)^k ~= 2^{-154} which is negligible
  -> one drawback: large public keys (nt bits = 256 * 2^{16} ~ 2.1 MB)
Solutions: HORST (HORS with Trees), the `t` components of `Y` are assigned to the leaves of a height-m Merkle tree. The root of the tree is Alice's public key.
Alice's signature on a message includes the components of Y needed to verify the signed message and also the authentication paths for each of these components.
A verifier can use the authentication paths to confirm the authenticity of the pk components included in the signature.

### Virtual Hypertrees
a virtual hypertree has L layers, each one consist of height-d Merkle trees, and every leaf of the Merkle trees in layers 1 to L-1 is associated with an OTS key pair.
  -> each OTS sk is used to sign the root of the tree beneath (sotto) it.
Every leaf of the Merkle trees in layer L is associated with an FTS key pair.
  -> the FTS sk are used to sign messages.
The root R of the hypertree is the user's long-term public key.

All OTS and FTS sk are derived by applying a PRF to a single secret SEED and a unique index identifying the correspondig pk.
The index might include the layer number, the tree identifier within that layer, and the public key's position within that tree
  -> once SEED is choosen, the entire hypertree is fully defined even though it might be infeasible to actually construct the entire tree 
     (this is the sense in which the hypertree is virtual)
Any individual Merkle tree can be efficiently constructed from SEED
